# CLAUDE.md

This file provides guidance to Claude Code when working with this repository.

## Project overview

`zenoai` is a TypeScript ESM CLI for JavaScript and TypeScript projects. It runs from the target project's current working directory, not from the Zeno repo, and supports two broad workflows:

- Phase 1 read-only health reports for SDE `Eyeball it` and EM `How bad is it` / `Triage it`.
- Phase 2 guarded refactoring for SDE `Humanise it`, `Slim it down`, and `Stress test it`.

The CLI supports Anthropic, Gemini, OpenAI, and OpenRouter using the provider stored in `~/.zenoai/config.json`.

## Commands

```bash
npm run build        # tsc -> compiles src/ to dist/
npm run dev          # tsx src/index.ts, useful during local development
node bin/zenoai.js   # runs compiled CLI after npm run build
npm run run:env      # loads .env then runs the compiled CLI
```

There are no automated tests or linter configured yet. `npm run build` is the baseline verification command.

## Architecture

```text
bin/zenoai.js              CLI entry, manually loads .env, then imports dist/index.js
src/index.ts               prompts for role/action and routes to Phase 1 or Phase 2
src/config.ts              first-run provider/API key setup in ~/.zenoai/config.json
src/core/analyst.ts        local JS/TS scan, static metadata, dependency graph
src/core/orchestrator.ts   Phase 1 report flow and Phase 2 coordinator
src/core/planner.ts        chooses safe files for a refactor run
src/core/reviewer.ts       asks LLM for conservative change instructions
src/core/validator.ts      rewrites a file and applies local confidence checks
src/core/critic.ts         post-refactor boundary-quality audit
src/core/differ.ts         writes accepted files, commits on zeno branch, asks approval
src/core/preflight.ts      git safety, dirty tree prompt, zeno branch lifecycle
src/core/history.ts        .zeno-history.json accepted/skipped tracking
src/utils/llm.ts           shared provider-agnostic LLM completion helpers
```

Phase 1 data flow:

```text
Analyst -> compact file summary -> one LLM call -> HealthReport JSON -> terminal report/cache/export
```

Phase 2 data flow:

```text
Preflight -> Analyst -> Planner -> Reviewer -> Validator -> Critic -> Differ -> Approval
```

## Current behavior

- Supported source files: `.ts`, `.tsx`, `.js`, `.jsx`.
- Skipped directories: `node_modules`, `dist`, `.git`, `.next`, `coverage`, `out`, `build`.
- Declaration files `.d.ts` / `.d.tsx` are skipped as generated/type output.
- Git submodules are detected from `.gitmodules` and excluded from analysis.
- Phase 1 analyzes large files and sends up to the 50 highest-risk files by `lines * functions`.
- Phase 2 selects up to 5 files from up to 20 planner candidates.
- Phase 2 currently skips autonomous whole-file refactors over 300 lines.
- EM actions are read-only and must not create zeno branches.
- SDE refactor actions create a `zeno/refactor-...` branch and require user approval before merge.

## Key constraints

- ESM throughout: keep `.js` extensions on internal imports.
- Do not assume `process.cwd()` is this repository; it is the project being analyzed/refactored.
- Do not bypass preflight for file-writing Phase 2 actions.
- Do not route EM actions into `runPhase2`.
- Keep Phase 1 read-only: no git branches, no file writes in the target repo.
- `dist/` is generated by `npm run build`; source changes belong under `src/`.
- Use `generateCompletion` and `extractJson` for shared LLM calls unless there is a specific reason not to.
